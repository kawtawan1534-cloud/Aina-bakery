Workflow Rules — กติกาการทำงานของไอ
(แยกจาก Engine.txt / Patch_Log.txt โดยเจตนา — ไฟล์นี้ไม่ใช่ logic เกม
 แต่เป็นกติกาว่าไอควรทำงาน/สื่อสารยังไงระหว่างเล่น)
═══════════════════════════════════════
 ตั้งแต่ Patch 6.0.0: ให้เริ่มต้นอ่านจากไฟล์ Parallel Engine Core.ps1 (orchestrator หลัก) และไฟล์ layer ที่เกี่ยวข้องใน Layers\ เท่านั้น (engine หลักตัวจริง — เดิมชื่อ Engine Noname.ps1 ก่อน Patch 6.0.0) แล้วทำตามขั้นตอนในไฟล์นั้นทีละขั้นตอนเท่านั้น — Engine Noname.txt แช่แข็งเป็น snapshot ประวัติ ใช้อ้างอิงแนวคิด/pipeline เดิมได้ แต่ไม่ใช่ตัวที่ต้องทำตามอีกต่อไป หากไม่พบหรือชื่อไฟล์ผิด แม้แต่ตัวเดียว ให้แจ้งเตือนเป็น error code ได้เลย

หาดตรวจสอบว่าพบเป็นเวอร์ชั่นที่ตรงกันแล้วแต่ในไฟล์ดังกล่าวดึงข้อมูลอ้างอิงจากไฟล์อื่นๆผิดพลาดไม่ว่าจะเป็นสูตร, การคำนวน หรือการอ้างอิง ให้แสดง error ทันที

1) Files are the Authoritative Source of Truth
   - ไฟล์ในโปรเจกต์ (Parallel Engine Core.ps1 + Layers\, Recipe, Stock, Production, ฯลฯ)
     คือแหล่งความจริงสูงสุดเสมอ — ตั้งแต่ Patch 5.0.0 ไฟล์ .ps1 แทนที่
     Engine Noname.txt ในฐานะ source of truth ของ logic (Engine Noname.txt
     แช่แข็งแล้ว ใช้อ้างอิงประวัติ/แนวคิดเท่านั้น — ตั้งแต่ Patch 6.0.0 ไฟล์ .ps1
     นั้นคือ Parallel Engine Core.ps1 + Layers\ เดิมชื่อ Engine Noname.ps1)
   - ไอต้องอ่านไฟล์จริงก่อนตอบทุกครั้ง ห้ามใช้ความจำ (Memory) มา
     ยืนยันตัวเลข/สถานะ/logic ใด ๆ — Memory ใช้ได้แค่บรรยากาศ/บริบททั่วไป (locked)
 
2) Active Scope Confirmation
   - ก่อนคำนวณหรือดำเนินการใด ๆ ไอต้องประกาศชัดเจนก่อนว่ากำลังอ้างอิง
     ไฟล์ไหน / layer ไหน เพื่อป้องกันข้อมูลข้ามไฟล์ปนกัน (cross-file
     contamination)
 
3) State Table as Session Handoff
   - State Table ตัวจริงคือไฟล์ sim_state.json ในโฟลเดอร์โปรเจกต์นี้ (ดูตาราง
     ไฟล์ใน CLAUDE.md) — ไม่ใช่ Memory ของไอ และ**ห้ามอยู่นอกโฟลเดอร์โปรเจกต์
     เด็ดขาด** (เคยพลาดเก็บไว้ที่ scratchpad มาแล้ว ห้องใหม่หาไฟล์ไม่เจอ)
   - ห้องแชทใหม่: อ่าน sim_state.json ตรงๆ ได้เลย ไม่ต้องให้ผู้เล่นก็อป
     ข้อความมาวางเอง (ยกเว้นไฟล์หายจริงๆ ค่อยขอให้ผู้เล่นช่วยยืนยันตัวเลข)
   - ก่อนจบ session หรือเปลี่ยนห้องแชท ไอสรุป State Table แบบย่อ (เงินสด,
     สต็อกวัตถุดิบ, customer history ฯลฯ) ให้ผู้เล่นดูได้ แต่ไฟล์ sim_state.json
     ต่างหากที่เป็นตัวจริงที่ใช้ต่อเกมได้
   - sim_daily_log.json คือแหล่งข้อมูลตัวจริงสำหรับ**วิเคราะห์ย้อนหลังข้ามวัน**
     (ต่างจาก sim_state.json ที่เก็บแค่ state ปัจจุบัน) — engine (Parallel Engine Core.ps1) append เข้าไฟล์
     นี้ทุกครั้งที่รัน ไม่ overwrite ของเก่า สะสมไปเรื่อยๆ ไม่ว่าจะย้ายห้องกี่รอบ
     ก็ตาม
   - ไม่ต้องอ่านไฟล์นี้ทุกวัน (ตามหลักประหยัด context ข้อ 11 — ข้อมูลวันที่เพิ่ง
     รันอยู่ใน context อยู่แล้วจากการคำนวณเอง) อ่านเฉพาะ 3 จังหวะนี้เท่านั้น:
       ก) เริ่ม session ใหม่/ย้ายห้อง (จุดที่ context ประวัติหายจริง)
       ข) ผู้เล่นถามคำถามเชิงวิเคราะห์ข้ามวันตรงๆ (เช่น "ทำไมลูกค้าลด"
          "ทำไมผลิตไม่พอขาย" "มีบัคไหม") ห้ามเดาจากความจำแชท
       ค) ก่อนเสนอไอเดีย/ตัวเลือกใน AskUserQuestion ที่อ้างอิงแพทเทิร์นข้าม
          **หลายวัน** (ไม่ใช่แค่เทียบกับเมื่อวานซึ่งมีอยู่ในมืออยู่แล้ว)
 
4) Minimal First, Patch Later
   - เริ่มต้นจากระบบที่มินิมอลที่สุดเสมอ (Gen 1: ไม่มี randomization
     ซับซ้อน ไม่มี AI decision-making ไม่มี conditional ซับซ้อน)
   - ห้ามเพิ่ม feature หรือความซับซ้อนที่ไม่ได้ถูกร้องขอ แม้จะดู
     "น่าจะมีประโยชน์" ก็ตาม — รอให้ผู้เล่นสั่งเพิ่มเองผ่าน Patch
 
5) Engine ต้องสมบูรณ์ในตัวเอง (Self-Contained)
   - Logic/สูตร/เงื่อนไขที่ "ใช้งานจริง" ต้องอยู่ใน Parallel Engine Core.ps1
     หรือไฟล์ layer ใน Layers\ เท่านั้น (ตั้งแต่ Patch 5.0.0 เป็นไฟล์ .ps1 —
     ก่อนหน้านั้นคือ Engine noname.txt, ตั้งแต่ Patch 6.0.0 แยกเป็น
     Parallel Engine Core.ps1 + Layers\ เดิมชื่อ Engine Noname.ps1)
   - Patch_Log.txt เก็บได้แค่ "สรุปว่าเปลี่ยนอะไร ทำไม เมื่อไหร่"
     ห้ามเป็นที่เก็บ logic ตัวเดียวที่มีอยู่ (เพราะถ้า archive
     Patch log เก่าทิ้งในอนาคต logic จะหายไปด้วย)
   - ตัวชี้วัด: "ถ้าไอไม่เห็น Patch Log เลย จะคำนวณผิดไหม?"
     ถ้าผิด แปลว่าต้องอยู่ใน engine ด้วย
 
6) 6) Patch Numbering (X.Y.Z)
   X = เปลี่ยนโครงสร้าง Engine / เพิ่ม-ตัด layer ทั้งกล่อง
   Y = ปรับ logic สูตร โค้ด หรือการคำนวณ (โครงสร้างเดิม)
   Z = แก้บัค ปรับราคา ปรับจูนเล็กน้อย
   - ขยับหลักไหน หลักที่อยู่ขวากว่ารีเซ็ตเป็น 0
     (เช่น 4.1.2 → เปลี่ยน logic ใหม่ = 4.2.0)
   - ขอบเขตเดิมของ X.Y.Z คือ engine (Parallel Engine Core.ps1/Layers\)
     เท่านั้น — Report Format.txt/Workflow Rules.txt/Patch Draft.txt ไม่นับ
     ปกติ **แต่ผู้เล่นมีดุลยพินิจสั่งข้อยกเว้นเป็นเคสๆ ได้** ถ้าตัดสินว่าการแก้
     ไฟล์เหล่านี้นับเป็น "แก้บัค" จริง (เช่น กติกาที่เขียนไว้แต่แรกไม่ครอบคลุม
     พอจนเกิดความเข้าใจผิด/พฤติกรรมผิดจริง) — ไอจะไม่ตัดสินเองว่าเข้าเกณฑ์
     ต้องรอผู้เล่นสั่งชัดเจนแบบนี้ทุกครั้ง
   - ตั้งแต่ Patch 6.1.0 เป็นต้นไป: หัวข้อ entry ทุกอันใน Patch_Log.txt ต้องมี
     วันที่+เวลาที่บันทึก กำกับท้ายบรรทัดหัวข้อเสมอ รูปแบบ
     `(บันทึกเมื่อ: YYYY-MM-DD HH:MM)` — ใช้เวลา ณ ขณะบันทึก entry จริง มีไว้
     เทียบว่าอัพแพทตรงกันไหมระหว่างเครื่องที่เล่น (ผู้เล่นใช้ 2 เครื่อง) entry
     ก่อนหน้า Patch 6.1.0 ไม่มีวันที่กำกับ (ห้ามย้อนไปเติมเดา เพราะไม่มีข้อมูลเวลา
     จริงของตอนนั้น — เป็นแค่จุดเริ่มต้นของ convention นี้ ไม่ใช่การลบ/แก้ entry เก่า)

7) Patch Draft Testing Mode
   - แนวคิด/ฟีเจอร์ใหม่ (เช่น ระบบขนมเมื่อวาน/หมดอายุ) ให้เขียนเป็น
     ไฟล์ร่างแยกก่อนเสมอ (เช่น Patch_5_draft.txt หรือ block แยกในไฟล์ layer
     ที่เกี่ยวข้อง ที่ยังไม่ merge เข้า main logic) ห้ามแก้ Parallel Engine Core.ps1
     หรือไฟล์ใน Layers\ หลักตรง ๆ ทันที
   - **ตั้งแต่การเปลี่ยนกติกาข้อนี้ (2026-08-09): คำสั่ง "ดราฟ" เพียงคำเดียว
     รวมทั้งขั้นเขียนร่าง + คำนวณ/รันทดสอบทันทีในสถานะ 🟡 UNLOCKED** ไม่ต้องรอ
     คำสั่งแยก "ทดลองรัน Patch X draft" อีกต่อไป (เดิมแยก 2 คำสั่ง — ตอนนี้รวม
     เป็นคำสั่งเดียว) พูดง่ายๆ คือ "ดราฟ" = เขียนร่าง + เทส/คำนวณให้ดูเลย,
     "แพท"/"อัพแพทลง engine" ยังคงเป็นคำสั่งแยกต่างหากเสมอ (ไม่ auto ต่อจาก
     ดราฟ) — ไอจะไม่แก้ Parallel Engine Core.ps1/Layers\ หลักจนกว่าจะได้รับ
     คำสั่งแพทชัดเจน
   - เมื่อเข้าโหมดทดสอบ (ระหว่างคำสั่ง "ดราฟ") ไอต้องประกาศ Active Scope
     แบบ 🧪 ให้ชัดว่ากำลังรันแบบ engine จริง (baseline) + Patch draft (overlay)
   - **รอบแรกตอนสั่ง "ดราฟ" (ยืนยัน logic ถูกต้อง): State แยกขาดจาก State
     จริงเสมอ (Option A)** — รันในสำเนาแยก (เช่น scratchpad) เงินสด/สต็อกที่
     เห็นตอนนี้เป็นแค่ค่าจำลอง ไม่กระทบ State Table จริงของเกม ใช้ยืนยันว่า
     logic ถูกต้องก่อนเท่านั้น
   - **ตั้งแต่การเปลี่ยนกติกาข้อนี้ (2026-08-10): หลังยืนยัน logic ถูกต้องแล้ว
     ตราบใดที่ draft ยังอยู่สถานะ 🟡 UNLOCKED ทุกครั้งที่ "รันต่อ" เกมจริงตามปกติ
     (ไม่ใช่แค่ตอนทดสอบ) ไอต้องรวม overlay ของ draft UNLOCKED นั้นเข้ากับ
     การคำนวณจริงด้วย (Option B)** — มีผลกระทบต่อ `sim_state.json`/
     `sim_report.json`/`sim_daily_log.json` จริงทันที ไม่ใช่ค่าจำลองอีกต่อไป
     แต่ไฟล์ `Parallel Engine Core.ps1`/ไฟล์ layer ใน `Layers\` ตัวจริงยังคง
     ข้อความเดิมทุกตัวอักษร ไม่ถูกแก้จนกว่าจะได้รับคำสั่ง "แพท" ชัดเจน — วิธี
     ทำทางเทคนิค: ไอใช้สำเนา engine ชั่วคราวที่มี overlay logic ผสมเข้าไป แต่
     ชี้ StatePath/ReportPath/LogPath ไปที่ไฟล์จริงของโปรเจกต์ ให้ state จริง
     อัปเดตได้โดยไม่ต้องแก้ไฟล์ .ps1 ตัวจริงในโปรเจกต์ — **โค้ด PowerShell
     จริงของ overlay ต้องเขียนไว้เป็น source of truth ใน Patch Draft.txt เอง
     (ไม่ใช่แค่คำอธิบายภาษาคน)** ตอนรันจริงไอคัดลอกก้อนโค้ดนั้นจาก
     Patch Draft.txt มาใส่ในสำเนาชั่วคราวตรงๆ ไม่แต่งขึ้นใหม่จากความจำ
     เพื่อการันตีว่าโค้ดที่รันจริงตรงกับที่บันทึกไว้ในดราฟเป๊ะ
   - ถ้ามี draft 🟡 UNLOCKED มากกว่า 1 อันพร้อมกัน ต้องรวม overlay ทุกอันเข้า
     ด้วยกันตอนรันจริง ไม่ใช่เลือกใช้แค่อันเดียว
   - ทุกรายงานระหว่างช่วงที่มี overlay ทำงานอยู่ ต้องระบุใน Active Scope
     Confirmation ให้ชัดว่ากำลังรันด้วย overlay ของ draft ตัวไหนอยู่บ้าง
     (ไม่ใช่แค่บอกว่ามี UNLOCKED ค้างอยู่เฉยๆ)
   - ยกเลิก overlay เมื่อ: ผู้เล่นสั่ง "แพท" (ย้าย logic เข้า engine จริงถาวร
     แล้วลบ block ออกจาก Patch Draft.txt ตามปกติ) หรือสั่งยกเลิก/ล็อกกลับ
     draft นั้น (overlay หยุดมีผลทันที ค่าที่คำนวณไปแล้วด้วย overlay ก่อนหน้า
     ไม่ย้อนแก้ตามหลัก "ห้ามแก้ประวัติที่บันทึกไปแล้ว")
   - ผลทดสอบไม่ผ่านตั้งแต่รอบแรก (Option A) → ไม่ปลด UNLOCKED ให้มีผลกับ
     state จริง เก็บบันทึกไว้กันคิดซ้ำ ไม่แตะไฟล์ engine หลักเลย

8) หน่วยวัด
   - หน่วยแสดงผล/จัดเก็บ (stockMax, stock): กิโลกรัม (kg) และลิตร (L)
   - หน่วยคำนวณสูตรอาหาร (recipe, costRates): กรัม (g) และมิลลิลิตร (mL)
   - แปลงหน่วยที่ normalizeStock() จุดเดียวเท่านั้น ห้ามเขียนสูตรแปลงซ้ำที่อื่น
     (แก้ไขจากต้นฉบับที่พิมพ์ผิด "กรัม (kg) และมิลลิลิตร (L)" เทียบกับ
     CLAUDE.md และ Stock เริ่มต้น.txt แล้วสรุปเป็นแบบนี้)

 9) Patch Application Flow (ทำงานแบบนักพัฒนาเกม)
   - ผู้เล่นเป็นคนเขียนไฟล์ Patch เอง ไอไม่สร้างให้เองโดยพลการ
   - เมื่อผู้เล่นอัปโหลด Patch ใหม่ ไอต้องตรวจ "ความเข้ากันได้"
     กับระบบเดิมก่อนเสมอ แล้วรายงานให้ดู:
       ก) ชนกับ logic ของ layer ไหนบ้าง
       ข) อ้างอิงไฟล์/ตัวเลขครบถ้วนพอคำนวณจริงได้ไหม
       ค) ผลกระทบต่อ layer อื่นที่อาจมองข้าม
       ง) จุดที่คลุมเครือจนคำนวณได้หลายแบบ
   - ไอต้องบอกตรง ๆ ถ้าเห็นว่าจะพัง หรือมีทางที่ดีกว่า
     ห้ามเออออตามอย่างเดียว
   - คุยกัน/แก้ร่วมกันจนโอเค → ผู้เล่นตัดสินใจเองว่าจะ patch
     ลง engine (Parallel Engine Core.ps1 / ไฟล์ layer ใน Layers\) หรือไม่
   - ไอจะไม่แตะ Parallel Engine Core.ps1 หรือไฟล์ layer (main logic) จนกว่าจะได้คำสั่งชัดเจนว่า
     "patch ลง engine"
   - เมื่อได้รับคำสั่งแล้ว ถามก่อนทุกครั้งว่าจะให้
     (ก) สร้างไฟล์ engine ฉบับใหม่ให้ทั้งไฟล์ (Parallel Engine Core.ps1 หรือไฟล์ layer ที่เกี่ยวข้อง) หรือ
     (ข) แจ้งเฉพาะจุดที่ต้องแก้ ให้ผู้เล่นไปแก้เอง
   - ไฟล์ engine มีแค่โค้ด/สูตร/ตัวเลขปัจจุบันล้วนๆ (เหมือนสูตรเลข
     `1+2*3/4` — เห็นแค่ผลลัพธ์สุดท้าย ไม่มีป้ายบอกว่า `/4` มาจากไหน) **ห้ามมี
     ป้ายอ้างอิงเลขแพทช์ ("Patch X (merged)" ฯลฯ) หรือประวัติ/เหตุผลเทียบ
     เวอร์ชันเก่า/ทางเลือกที่ปฏิเสธไป/ผลการทดสอบ ปนอยู่ในคอมเมนต์เลยแม้แต่
     บรรทัดเดียว** — ของพวกนี้อยู่ที่ Patch_Log.txt ทั้งหมดแล้ว ห้ามซ้ำ
   - คอมเมนต์ใส่ได้เฉพาะตอนโค้ดจุดนั้นดูขัดสามัญสำนึก/ไม่สมมาตรจนอาจถูกเข้าใจ
     ผิดว่าเป็นบั๊ก (เช่น floor() ตอนลดแต่ ceil() ตอนเพิ่ม) — อธิบายแค่ตรรกะที่
     จำเป็นต่อการอ่าน/แก้โค้ดสั้นๆ ไม่อ้างเลขแพทช์หรือประวัติใดๆ อยากรู้ที่มา/
     ทดสอบผ่านยังไง ให้เปิด Patch_Log.txt เอง

10) การรายงานผล
   - ไม่ต้องประกาศย้ำว่ากำลังทำตาม Workflow Rules ข้อไหน
   - ไม่ต้องเตือนซ้ำเรื่องที่ผู้เล่นยืนยันไปแล้ว
   - แต่ถ้าพบ error (ไฟล์ขัดแย้งกันเอง, สูตรไม่ตรง, อ้างอิงผิด,
     เวอร์ชันไม่ตรง) ให้แจ้งทันทีเสมอ
   - เมื่อผู้เล่นแก้ไฟล์แล้วบอกให้อ่านใหม่ → ตรวจว่า logic
     สอดคล้องกันทั้งระบบไหม แล้วรายงานให้ผู้เล่นยืนยัน
11) การอ่านไฟล์อย่างประหยัด Context
   - ทุกครั้งที่ไอเปิดอ่านไฟล์ เนื้อหาทั้งไฟล์ถูกโหลดเข้า context
     ใหม่ทั้งหมด (แม้เคยอ่านแล้ว) → อ่านซ้ำบ่อยทำให้ context
     เต็มเร็ว และของเก่าจะถูกทิ้ง
   - ระหว่างเล่นปกติ: คำนวณต่อจากรอบที่แล้วได้เลย
     ไม่ต้องอ่านไฟล์ซ้ำทุกวัน
   - ข้อยกเว้น: **Report Format.txt อ่านใหม่ทุกครั้งก่อนสร้างรายงานประจำวัน
     เสมอ ไม่ต้องรอผู้เล่นบอกว่าแก้แล้ว** — ไฟล์เล็ก กิน context น้อยมาก แต่
     ผู้เล่นแก้ไฟล์นี้ได้ทุกเมื่อโดยไม่บอกไอก็ได้ (ดูข้อ 13) ถ้าไม่อ่านใหม่ทุกวัน
     จะมีช่วงที่ไอใช้ format เก่าที่จำจากแชทแทนไฟล์จริงโดยไม่รู้ตัว (พบเป็นช่องโหว่
     จริงระหว่างคุยเรื่อง Memory Layer)
   - ข้อยกเว้นอีกข้อ: **ตัวตนไอ.txt อ่านอัตโนมัติทันทีที่เริ่ม session ใหม่/
     ย้ายห้องแชท (ไม่ต้องให้ผู้เล่นสั่งทุกครั้ง)** แล้วใช้บุคลิก/โทนเสียง/ลักษณะ
     การใช้อิโมจิตามไฟล์นั้นตลอด session — ไม่ต้องอ่านซ้ำระหว่างเล่นต่อเนื่อง
     ในห้องเดิม (ต่างจาก Report Format.txt ที่อ่านซ้ำทุกรายงาน) ยกเว้นผู้เล่น
     แจ้งว่าแก้ไฟล์นี้แล้วระหว่างเล่น ก็อ่านใหม่เฉพาะตอนนั้น — กติกา Report
     Format.txt (ห้ามเกริ่นอารมณ์ก่อนหัวเรื่อง, ต้องใช้ code block ฯลฯ) ยังคง
     บังคับเหนือกว่าบุคลิกนี้เสมอเมื่อขัดกัน (ดูรายละเอียดเต็มที่ ตัวตนไอ.txt)
   - อ่านไฟล์ใหม่เมื่อ:
     ก) ผู้เล่นสั่งให้อ่าน (เช่น เจอบัค/ตัวเลขรวน)
     ข) ผู้เล่นแจ้งว่าแก้ไฟล์แล้ว → อ่านเฉพาะไฟล์นั้น
        (ถ้าระบุบรรทัดมาด้วย อ่านเฉพาะช่วงนั้นพอ)
     ค) เริ่ม session ใหม่ / ต่อจาก State Table
   - ถ้าไอเองไม่แน่ใจว่าตัวเลขที่ใช้อยู่ตรงกับไฟล์จริงไหม
     ให้ถามผู้เล่นก่อนว่าจะให้อ่านไฟล์ใหม่หรือไม่
     ห้ามเดาแล้วคำนวณต่อ

12) Debug Mode — โหมดตรวจสอบบัค
   เข้าโหมดเมื่อ:
     ก) ผู้เล่นสั่ง "เข้าโหมดตรวจสอบบัค"
     ข) ไอเจอความผิดปกติเอง (ตัวเลขไม่สมเหตุสมผล, คำนวณแล้ว
        ขัดกับรอบก่อน, สูตรให้ผลหลายแบบ) → แจ้งผู้เล่นทันที
        แล้วถามว่าจะเข้าโหมดตรวจสอบไหม ห้ามเดาแล้วคำนวณต่อ

   ระหว่างอยู่ในโหมด:
     - หยุดเดินเกม ไม่ขึ้นวันใหม่จนกว่าจะออกจากโหมด
     - อ่านไฟล์ที่เกี่ยวข้องใหม่ทั้งหมด (ยกเว้นการประหยัด
       context ชั่วคราว — ความแม่นยำมาก่อน)
     - เทียบ 3 ทาง: ไฟล์จริง vs ตัวเลขที่ใช้คำนวณอยู่ vs
       State Table ล่าสุด
     - รายงานเป็นตาราง: จุดไหนตรง / จุดไหนไม่ตรง / ต่างกันเท่าไร
     - ไม่แก้ไฟล์เอง เสนอจุดที่ควรแก้ให้ผู้เล่นตัดสินใจ

   ออกจากโหมดเมื่อ:
     - ผู้เล่นยืนยันว่าจุดที่พบถูกต้องแล้ว หรือสั่งให้เล่นต่อ
     - ไอสรุปว่าใช้ตัวเลขชุดไหนเป็นหลักในการเล่นต่อ

13) Report Format
   - หน้าตา/โครงสร้างของรายงานผลจำลองรายวัน (หัวข้อ [1]-[7], เมนูปุ่มท้าย
     รายงาน ฯลฯ) อยู่ที่ Report Format.txt เป็นไฟล์เดียว — ไม่ใช่ Workflow
     Rules.txt (ไฟล์นี้ดูแค่กติกาการทำงาน ไม่ใช่หน้าตารายงาน)
   - ผู้เล่นแก้ Report Format.txt เองได้ทุกเมื่อเพื่อเปลี่ยนรูปแบบรายงาน โดย
     **ไม่ต้องบอกไอก็ได้** — ไออ่านไฟล์นี้ใหม่เองทุกครั้งก่อนสร้างรายงานอยู่แล้ว
     (ข้อยกเว้นตามข้อ 11) แล้วใช้รูปแบบล่าสุดทันที ไม่ต้องรอคำสั่งอื่นเพิ่ม
