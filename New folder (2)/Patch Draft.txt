Patch (Y): เพิ่มปัจจัยภายนอกมาปรับ p (และ N) ของ Patch 5.1.0 ให้ร้านโต/หดได้
ระยะยาว (ต่อยอดจาก Patch 5.1.0 ซึ่ง merge แล้ว — พร้อมทำได้เมื่อไหร่ก็ได้)

  📌 ค่าคงที่ที่เป็น "จุดเกาะ" ให้ฟังก์ชันในอนาคตมาครอบ: **`N = 30` และ `p = 0.35`
     ต้องปรับได้ทั้งคู่ ไม่ใช่แค่ p ตัวเดียว** (ใน GenerateDailyCustomers() ของ
     Patch 5.1.0) — เช็คแล้วพบว่าถ้าปรับแค่ p อย่างเดียว จะชนเพดานลับๆ ที่ N
     เสมอ: Binomial(N,p) เฉลี่ย = N×p ต่อให้ p→1 (เกือบทุกคนแวะทุกวัน) เฉลี่ยก็
     ยังตันที่ N=30 อยู่ดี เพราะ N คือ "จำนวนคนทั้งหมดที่มีสิทธิ์แวะ" ต่อให้รีวิว/
     คะแนนร้านดีสุดขีดแค่ไหนก็ทะลุ 30 ไม่ได้ถ้า N ไม่ขยับตาม
     - p คุม "ความน่าดึงดูดวันนั้น" (รีวิว, เทศกาล, ฝนตก ฯลฯ ตามด้านล่าง)
     - N คุม "ขนาดตลาด/การเข้าถึง" (ร้านเป็นที่รู้จักกว้างขึ้น, เปิดเดลิเวอรี่ ฯลฯ)
       ต้องมีปัจจัยขยับ N ระยะยาวด้วย ไม่งั้น growth จะเข้าใกล้เพดาน 30 แล้ว
       แบนราบตลอดไปไม่ว่า p จะดีแค่ไหน

  📌 แนวคิดสูตรเป้าหมาย (ยังไม่ล็อกตายตัว แค่โครงคร่าวๆ):
     p = pฐาน(0.35) + ผลรวมปัจจัยรายวัน/ระยะยาวด้านล่าง (คุมความน่าดึงดูด)
     N = Nฐาน(30) + ผลรวมปัจจัยขยายตลาดระยะยาว (คุมเพดาน — ยังไม่คิดรายละเอียด
     ว่าจะมีปัจจัยอะไรบ้าง แค่บันทึกไว้ว่า "ต้องมี" กันลืม)

  📌 รายการไอเดียปัจจัยที่คิดไว้ (แยกตามความเร็วที่เปลี่ยน — แต่ละอันคือแพทย่อย
     ในอนาคต ทำทีละอันได้ ไม่ต้องทำพร้อมกันหมด):

     ปัจจัยรายวัน (สุ่มใหม่ทุกวัน — ยังคุม/ทำนายไม่ได้เหมือนเดิม):
     • ฝนตก — ลด p วันนั้น (คนออกจากบ้านน้อยลง)
     • เทศกาล/งานแถวนั้น — เพิ่ม p วันนั้น (คนพลุกพล่านกว่าปกติ)

     ปัจจัยระยะยาว (ขยับช้าๆ สะสมข้ามหลายวัน — ช่องทางที่ทำให้ "ร้านโต" ได้จริง):
     • รีวิว/คะแนนร้าน — สะสมจากผลงานร้าน (ของไม่ขาดบ่อย ฯลฯ) ค่อยๆ ดัน p ขึ้น
     • ลูกค้าประจำ — นับคนที่แวะซ้ำหลายครั้ง ค่อยๆ ดัน p ขึ้นต่างหากจากรีวิว

  📌 ข้อดีที่ยังจริงอยู่ (แก้ความเข้าใจผิดรอบแรกแล้ว): ไม่ต้องมี maxCustomers
     แยกต่างหากเหมือนระบบเก่าอีก เพราะ N เป็นเพดานในตัวอยู่แล้ว — **แต่ต้องตั้งใจ
     ให้ N ขยับได้ระยะยาวด้วย** (ตามข้อบนนี้) ไม่งั้นเพดานที่ว่าจะกลายเป็นเพดาน
     ตายตัวที่ทำให้ร้านโตได้ไม่จริงในระยะยาว

  📌 หมายเหตุ: ข้อ "รีวิว/คะแนนร้าน" จะไปเชื่อมกับแนวคิดระบบ rating ที่เคยพักไว้
     ก่อนหน้านี้ — ยังไม่ต้องคุยรายละเอียดตอนนี้ พอถึงเวลาทำจริงค่อยว่ากัน

  ⚠️ บัคที่รู้แล้ว — วงจรแกว่งสวนทางกัน (out-of-phase feedback loop) ระหว่าง
     production กับ p/N growth (ผู้เล่นชี้จุดนี้เอง 2026-08-13 — ยังไม่คิดวิธีแก้
     ไม่แตะโค้ด/JSON ใดๆ แค่กำกับไว้กันลืม):
     - `AutoProductionOrder()` (`01_AutoProductionOrder.ps1`) ปรับยอดผลิตจาก
       sold/produced/ordered ของ**เมื่อวาน** (มี lag 1 วันเสมอ) ส่วน
       shopRating/loyaltyPool (ดราฟนี้) ก็ตอบสนองต่อ walkedAway ทันทีด้วย lag
       เดียวกัน — ทั้งสองระบบไม่คุยกันเลย
     - วงจรที่จะเกิด: วันลูกค้าเยอะ (p สูงจากเทศกาล) + ขนมมีจำกัด → ขายหมด +
       มีคนเดินหนีมือเปล่า → shopRating ลด + loyaltyPool รีเซ็ต 0 (ตาม
       satisfactionDelta ของดราฟนี้) → พร้อมกันนั้น AutoProductionOrder เพิ่ม
       ยอดผลิต ×1.2 (เพราะเห็นว่าขายหมดเมื่อวาน) → วันถัดไปขนมเยอะขึ้นแต่
       ลูกค้ากลับน้อยลง (p ที่เพิ่งร่วงจาก rating/loyalty) → ขายไม่หมด/เหลือทิ้ง
       → sellThroughRate ต่ำ → AutoProductionOrder ลดยอดผลิตกลับลง — แกว่ง
       ไป-มาแทนที่จะดันร้านให้โตสุทธิ
     - ต้องแก้ก่อนปลดล็อกดราฟนี้จริง มิฉะนั้นระบบ p/N growth อาจไม่ทำให้ร้านโต
       จริงตามที่ตั้งใจ (แค่แกว่งชดเชยตัวเอง) — วิธีแก้ยังไม่ตัดสินใจ รอผู้เล่นเคาะ

  📌 ข้อเสนอเต็มระบบจากไอ (2026-08-12 — ผู้เล่นขอแบบท้าทาย ยังไม่ยืนยันตัวเลข
     สักตัว แค่บันทึกกันลืมว่าเคยเสนอไว้แบบนี้ ต้องทดสอบสมดุลจริงก่อนล็อก):

     [1] ปัจจัยรายวัน (สุ่มอิสระทุกวัน ไม่สะสม):
       - ฝนตก: LFSR แยกจาก Customer Layer เดิม, โอกาส 20%/วัน, p -0.05
         วันนั้น
       - เทศกาล: โอกาส 5%/วัน, p +0.08 วันนั้น (เกิดพร้อมฝนตกได้ หักลบกันจริง)
       - **ย้ายไปรวมอยู่ใน Patch (Y) "ระบบเหตุการณ์สุ่มรายวัน" (20 เหตุการณ์)
         ท้ายไฟล์นี้แล้ว เป็นเหตุการณ์ที่ 1-2** ไม่ใช่ปัจจัยเฉพาะของ N/p patch
         อีกต่อไป — patch นี้ (N/p) จะ "รับผล" p bonus/malus จากระบบ event
         กลางแทนที่จะมี logic สุ่มของตัวเอง

     [2] รีวิว/คะแนนร้าน (ต้องสร้างระบบ rating ใหม่ทั้งหมด — ยังไม่เคยมีเลย):
       - state ใหม่ `shopRating` (0-100, เริ่ม 50)
       - ปรับทุกวันจาก satisfactionDelta: + ถ้าลูกค้าได้ของ fresh เยอะ
         (staleSold.fresh/totalSold สูง), − ถ้ามีคนเดินหนีเพราะของหมดจริง
         (ไม่นับ walkAwayChanceHits เพราะเป็นเดินหนีเอง ไม่ใช่ความผิดร้าน)
       - มี mean reversion ลอยกลับเข้าใกล้ 50 เองถ้าไม่มีอะไรผิดปกติต่อเนื่อง
       - p bonus = (shopRating-50) × 0.003 → เต็มเพดาน ±0.15 ที่ rating
         0/100

     [3] ลูกค้าประจำ (ท้าทายสุด — architecture เดิมไม่มีทาง track รายบุคคล
       เลย ต้องใช้ตัวแทนนามธรรมแทน):
       - state ใหม่ `loyaltyPool` (0-20) + `consecutiveGoodDays`
       - วันไหน walkedAway=0 (ไม่มีคนเดินหนีเพราะของหมด) →
         consecutiveGoodDays += 1, มีคนเดินหนีเพราะของหมด → รีเซ็ตเป็น 0
       - loyaltyPool = Min(20, consecutiveGoodDays × 0.5) — ทำดีติดต่อกัน
         40 วันถึงเต็มเพดาน (ตั้งใจให้สะสมช้าสมกับเป็นของระยะยาว)
       - p bonus = loyaltyPool × 0.005 → เต็มเพดาน +0.10

     [4] N (เพดานตลาด) — ปลดล็อกเป็นขั้นด้วย milestone ทั้งขึ้นและลง (ผู้เล่น
       ถามเองว่ามีทางลดไหม — เพิ่มเข้ามาให้สมดุล ไม่ใช่ทางเดียว):
       ขาขึ้น (milestone):
         • รายได้สะสมทั้งเกมถึง 100,000 บาท → N +5
         • shopRating เหนือ 80 ติดต่อกัน 30 วัน → N +5
         • รายได้สะสมถึง 300,000 บาท → N +10
       ขาลง (เสียชื่อเสียง/ตลาดหด):
         • shopRating ต่ำกว่า 20 ติดต่อกัน 30 วัน → N -5
         • walkedAway เพราะสต็อกขาด เกิดติดต่อกัน 15 วันขึ้นไป → N -3
       กติกาที่เสนอ (ยังไม่ยืนยัน): N มีพื้นขั้นต่ำ = 30 เสมอ (ไม่ลดต่ำกว่าจุด
       เริ่มเกม) และ N ที่เสียไปกู้คืนได้ถ้าทำ milestone เดิมผ่านซ้ำอีกรอบ
       (ให้โอกาสแก้ตัว ไม่ใช่พังแล้วจบเกม) — ใช้กลไก "นับวันติดต่อกัน" แบบ
       เดียวกับ `consecutiveDays` ของ Diminishing Appeal (Patch 6.2.3) ได้เลย
       ไม่ต้องคิดกลไกนับวันใหม่

     สูตรรวม: `p = 0.35 + ปัจจัยรายวัน + ratingBonus + loyaltyBonus`
     (clamp 0.05-0.95), `N = 30 + ผลรวม milestone ที่ปลดแล้ว (ลบล้างกันได้
     ถ้ามีทั้งขึ้นและลง)`

     ⚠️ state ใหม่ที่ต้องเพิ่มใน `sim_state.json` ถ้าทำจริง: `shopRating`,
     `consecutiveGoodDays`, `totalRevenueEarned` (สะสมทั้งเกม), และตัวติดตาม

       ส่งด่วน) หรือผู้เล่นเลือกเอง

  📌 ตัวเลขร่างตั้งต้น (ไอเดาเสนอมา — ผู้เล่นบอกชัดว่า "ยังไม่รู้ว่าโอเคป่าว
     เล่นไปเรื่อยๆ" คือยังไม่ยืนยัน/ยังไม่ตัดสินใจ แค่กันลืมว่าเคยเสนอไว้แบบนี้
     ต้องดูผลจริงตอนทดสอบก่อนค่อยฟันธง):
     - แบ่งประเภทวัตถุดิบ: ของสด (Milk, Egg) vs ของแห้ง (Flour, Sugar,
       Yeast, Redbean, Butter, Cocoa)
     - Lead time: เจ้าประจำ ของสด 1 วัน/ของแห้ง 2 วัน — เจ้าสำรอง ของสด
       1 วัน/ของแห้ง 1 วัน — เจ้าส่งด่วน 0 วันทั้งคู่ (มาถึงทันทีเหมือนระบบเดิม)
     - ราคาคูณจาก costRates ฐาน: เจ้าประจำ x1.00 — เจ้าสำรอง x1.15 —
       เจ้าส่งด่วน x1.50
     - MOQ = 20% ของ stockMax ต่อวัตถุดิบ (ปัดขึ้น)
     - เกณฑ์สลับ Supplier อัตโนมัติ (ร่าง): ต่ำกว่า threshold ปกติ → สั่งเจ้า
       ประจำ, ถ้าระหว่างรอของแล้วคำนวณว่าจะขาดก่อนของมาถึง (เช่น สต็อกจะ
       ต่ำกว่า threshold ครึ่งหนึ่ง) → สลับไปสั่งเจ้าส่งด่วนแทนอัตโนมัติ

  📌 จุด trigger สั่งซื้อต้องปรับด้วย เพราะมี lead time แล้ว (ผู้เล่นชี้จุดนี้เอง):
     ระบบเดิม reorderThreshold เป็นจุดเตือนที่ใช้ได้เพราะของมาถึงทันที
     (lead time=0) แต่พอมี lead time จริง ถ้ารอจนสต็อกต่ำกว่า threshold
     ค่อยสั่ง สต็อกจะหมดกลางทางก่อนของมาถึงจริง (ร้านยังต้องขายต่อระหว่าง
     รอของ) — ต้องขยับจุดสั่งซื้อให้เร็วขึ้นล่วงหน้าตาม lead time:
     - แนวคิดสูตร: จุดสั่งซื้อ = reorderThreshold + (อัตราใช้เฉลี่ยต่อวัน ×
       lead time ของ Supplier ที่จะสั่ง) — ยังไม่ล็อกตายตัวว่า "อัตราใช้เฉลี่ย
       ต่อวัน" คำนวณจากอะไร (เฉลี่ยย้อนหลังกี่วัน? จาก `needed` ของวันก่อนๆ?)
     - พอถึงจุด trigger แล้ว ต้อง**สั่งทันทีวันนั้นเลย ห้ามรอ/ห้ามเลื่อน** เพราะ
       ยิ่งสั่งช้าออกไปอีกวัน เวลาที่เหลือก่อนของหมดจริงก็ยิ่งกระชั้นขึ้นเรื่อยๆ
       (lead time ไม่ได้ลดลงตาม แต่เวลาที่เหลือให้ตัดสินใจลดลง)
     - ยังต้องคุยต่อ: threshold เดิม (`reorderThreshold`) จะยังใช้เป็นค่าตั้งต้น
       ของสูตรนี้ต่อไป หรือต้องคิดค่าใหม่ทั้งหมดแยกจากระบบเดิม

     25-50kg/ถุง, เนย 25kg/ก้อน) ใหญ่เกิน stockMax ปัจจุบันของเกมมาก (ร้าน

       packSize = 1 L/กล่อง ตามมาตรฐานกล่องนมทั่วไป (stockMax=5L → 5 กล่อง)
     • Cocoa (โกโก้): stockMax ปัจจุบัน = 0 (ยังไม่ได้ใช้งานจริงในเกม) — ยังไม่
       ต้องกำหนด packSize จนกว่าจะปลดล็อกเมนูที่ใช้จริง
     • Egg (ไข่): ยืนยันแล้วจากระบบเดิม = 30 ฟอง/แผง (ไม่ต้องหาข้อมูลเพิ่ม)
