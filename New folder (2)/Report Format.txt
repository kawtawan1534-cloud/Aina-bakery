[2] Stock Check — ตรวจสต็อก
─────────────────────────────────────
ทุกอย่างอยู่ใน 1 กล่องโค้ดเดียว (```...```) ไม่แยกนอกกล่อง — คอลัมน์ตรงกัน
แบบตาราง (วัตถุดิบ / มี / ใช้ / %) แต่เป็น plain text จัด space เอง ไม่ใช้
markdown table syntax (เล็กกว่า render เป็นตารางจริง) เรียงแถวจาก % ต่ำสุด
→ สูงสุด (แถวบนสุด = ตัวฉุดถ้ามี) ปิดท้ายด้วยสรุปผลแบบ bullet ในกล่องเดียวกัน:

```
วัตถุดิบ    มี         ใช้         %
{วัตถุดิบ}  {จำนวน}    {จำนวน}    {%}
... (ครบทุกวัตถุดิบที่ใช้ในคำสั่งผลิตวันนั้น)

➡️ สรุปผล: ผลิตได้ {%} ของคำสั่ง (ตาม{วัตถุดิบตัวฉุด ถ้ามี ratio<100%})
   • Shokupan: {n ผลิตวันนี้} ชิ้น {(+{n เหลือจากเมื่อวาน} เหลือจากเมื่อวาน =
     ขายได้สูงสุด {n รวม} ชิ้น) — ใส่เฉพาะเมนูที่มีของเหลือจากเมื่อวาน (soldLast
     < producedLast ของเมื่อวาน) ถ้าเมนูไหนขายหมดเกลี้ยงเมื่อวาน ไม่ต้องมีวงเล็บ
     นี้ต่อท้าย}
   • Melonpan: {n} ชิ้น {เหมือนกัน}
   • Anpan:    {n} ชิ้น {เหมือนกัน}
```

(เลขเหลือจากเมื่อวานมาจาก producedLast - soldLast ใน sim_state.json ของ
เมนูนั้น — เป็นแค่ข้อมูลอ้างอิงให้ดูเทียบ ไม่ได้บวกเข้าไปใน availableStock จริง
ของวันนี้ เพราะเอนจิ้นยังไม่มีระบบขนมเมื่อวานเก็บสต็อกข้ามวัน)

ตัวอย่าง (Shokupan เหลือจากเมื่อวาน 2 ชิ้น, Melonpan/Anpan ขายหมดเกลี้ยง):

[6] Reorder Logic
─────────────────────────────────────
ทั้งหมดอยู่ใน 1 กล่องโค้ด ทุกหัวข้อย่อยใช้ bullet (•) นำหน้าแต่ละแถว ไม่ใช่
บรรทัดเดียวแบบเก่า เรียงลำดับตายตัว: ⚠️ ใกล้หมด (ถ้ามี) -> 📦 หลังผลิต
(ถ้ามี reorder จริง) -> 🚚 เติม (ถ้ามี reorder จริง) -> รวมค่าสั่งของเพิ่ม

```
⚠️ ใกล้หมด:
   • {วัตถุดิบ} เหลือ {จำนวน} (จะเติมเมื่อต่ำกว่า {เกณฑ์เติมจริง})
   • ... (ถ้ามีหลายตัว — ถ้าไม่มีวัตถุดิบใกล้หมดเลย ข้ามหัวข้อ ⚠️ ทั้งบล็อกนี้)

📦 หลังผลิต:
   • {วัตถุดิบ} เหลือ {จำนวน} (เกณฑ์ {เกณฑ์}) ❌
   • ... (ถ้ามีหลายตัว)

🚚 เติม:
   • {วัตถุดิบ} +{จำนวน} ({ราคา} บาท)
   • ... (ถ้ามีหลายตัว)

รวมค่าสั่งของเพิ่ม: {reorderCost} บาท
```
(ถ้าไม่มีวัตถุดิบไหนโดน reorder จริงเลย แทนที่ 📦/🚚/รวมค่าสั่งของเพิ่ม ด้วย
บรรทัดเดียวในกล่องเดียวกัน: "✅ ทุกวัตถุดิบเหนือเกณฑ์ → ไม่ต้องสั่งเพิ่ม")

[7] Output (ยอดขาย)
─────────────────────────────────────
ทั้งหมดอยู่ใน 1 กล่องโค้ด:

```
เงินเริ่มต้น:      {cashStart}
+ รายได้ขาย:       +{revenue}
− ค่าสั่งซื้อ:       −{reorderCost}
− ค่าน้ำ/ไฟพื้นฐาน:  −{waterElecBase}
− ค่าไฟเตาอบ:       −{ovenElecCost}
− ค่าบรรจุภัณฑ์:     −{packagingCost}
{ถ้า rentCost > 0 เท่านั้น ใส่บรรทัดนี้เพิ่ม: "− ค่าเช่า:         −{rentCost}"}
─────────────────────
เงินสดคงเหลือ: {cashEnd} ✨ ({+/-ส่วนต่างจาก cashStart})

🌱 สถานะร้าน: ชื่อเสียง {shopRating}/100, ลูกค้าประจำ {loyaltyPool}/20
   (ดีต่อเนื่อง {consecutiveGoodDays} วัน), เพดานลูกค้า N={customerPoolN},
   โอกาสแวะร้าน p={customerVisitP×100}%
```
(บล็อก 🌱 นี้ใส่เฉพาะตอนระบบ N/p growth ปลดล็อกแล้ว — ถ้ายังไม่ปลดล็อกให้ข้าม
ทั้งบล็อกนี้ไป จบแค่บรรทัดเงินสดคงเหลือ — ตั้งแต่ Patch 6.6.1 ไม่มี milestone/
ขั้นบันไดอีกต่อไป ทั้ง N และ p ขยับต่อเนื่องตาม shopRating ล้วนๆ ทุกวันเหมือนกัน
ไม่มีรายได้สะสม/เกณฑ์ปลดล็อกใดๆ ให้แสดง)

─────────────────────────────────────
ปิดท้าย (ถ้ามีข้อสังเกตเด่นของวันนั้น)
─────────────────────────────────────
ใส่เฉพาะเมื่อมีอะไรน่าสังเกตจริงๆ (ไม่บังคับต้องมีทุกวัน) เช่น "ตัวที่ขาด" ซ้ำ
หลายวันติด, ลูกค้าเปลี่ยนทิศทางชัด, บัค/แพทที่เพิ่งยืนยันผลได้ ฯลฯ — เขียนเป็น
bullet ข้อละประเด็น (ไม่ใช่ย่อหน้าเดียวยาว) นำหน้าแต่ละ bullet ด้วยอิโมจิที่สื่อ
โทนของประเด็นนั้น (เช่น ✅ = ยืนยัน/ผ่าน, ⚠️ = ต้องระวัง/ตัวที่ขาด, 📈📉 = แนวโน้ม
ขึ้น/ลง) 1 ประโยคสั้นๆ ต่อ bullet ปกติมี 1-3 bullet ต่อรายงาน ไม่ต้องใส่ code
block (เป็นข้อความธรรมดาเหมือนเดิม)

เมนูปุ่มกดท้ายรายงาน (ใช้ AskUserQuestion)
─────────────────────────────────────
คำถาม: "จะให้ไอทำอะไรต่อคะ"
ตัวเลือก:
   1) "เปิดร้านต่อ (Recommended)" — **บังคับต้องมีเสมอทุกรายงาน** ตายตัว
      ห้ามเปลี่ยน (รันวันถัดไปด้วยกลไกทั้งหมดที่ปลดล็อกอยู่) ปรับได้แค่
      คำอธิบายท้ายให้ตรงวันถัดไป
   ข้อที่เหลือ) จำนวนไม่ตายตัว — **แล้วแต่สถานการณ์จริงของวันนั้น** ไม่ต้อง
      ยึดจำนวนคงที่ (ไม่ใช่ต้องมี 2 หรือ 3 ข้อเสมอ) เสนอเท่าที่มีเหตุผลจริงจาก
      รายงานวันนั้น ผูกกับ bullet ใน "ปิดท้าย" ได้โดยตรง (เช่น แพทเทิร์นที่
      น่าสนใจ, จุดที่น่าจะปรับออเดอร์, แนวคิด patch draft ใหม่) — ถ้าวันไหน
      ไม่มีอะไรน่าเสนอเลยจริงๆ ใช้ตัวเลือกทั่วไปแทนได้ (ดู State Table เต็ม /
      จัดการ Patch draft) รวมทั้งหมดต้องมีอย่างน้อย 2 ข้อเสมอ (ข้อบังคับ +
      อย่างน้อยอีก 1 ข้อ) และไม่เกิน 4 ข้อ (ข้อจำกัดของเครื่องมือ)
(ผู้เล่นพิมพ์คำตอบอื่นเองได้เสมอผ่านช่อง Other)
