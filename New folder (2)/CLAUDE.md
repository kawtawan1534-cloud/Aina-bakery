## เรโปนี้คืออะไร

**"Engine Noname"** คือเกมจำลองเศรษฐศาสตร์ร้านเบเกอรีแบบเทิร์นเบส ตั้งแต่ **Patch 5.0.0** engine ตัวจริงที่รันได้จริงคือไฟล์ `.ps1` (PowerShell) — ไม่ใช่ pseudocode ที่ต้องตีความด้วยหัวอีกต่อไป (ต่างจากก่อนหน้านี้) ตั้งแต่ **Patch 6.0.0** engine ถูกแยกเป็นสองส่วน: **`Parallel Engine Core.ps1`** (orchestrator หลัก — ชื่อเกม/โปรเจกต์ยังคงเป็น "Engine Noname" เหมือนเดิม แค่เปลี่ยนชื่อไฟล์ตัวเอนจิ้น) เชื่อมกับไฟล์ layer ทั้ง 8 ใน `Layers\` โฟลเดอร์ (dot-source เข้า scope เดียวกัน ทำงาน sequential เหมือนเดิมทุกประการ ไม่ใช่ parallel แม้ชื่อไฟล์จะมีคำนี้อยู่ก็ตาม — ดู pipeline ด้านล่าง) ไฟล์ `Engine Noname.txt` **แช่แข็งเป็น snapshot ประวัติที่ 4.5.0** ไว้อ่านอ้างอิง pipeline/แนวคิดเดิมเท่านั้น ไม่อัปเดตตามอีกแล้ว และไม่ใช่ source of truth ของ logic ปัจจุบัน

ถึงอย่างนั้นก็ยังไม่ใช่โปรเจกต์ซอฟต์แวร์แบบมาตรฐาน — ไม่มี build system, package manager, linter หรือ test runner "การพัฒนา" หมายถึงการแก้ไข/ต่อเติม `Parallel Engine Core.ps1` และ/หรือไฟล์ layer ใน `Layers\` โดยตรง พร้อมรักษาให้ `Patch_Log.txt` สอดคล้องกันเสมอ (ทุกแพทช์ต่อจากนี้อ้างอิง `Parallel Engine Core.ps1` + `Layers\` แทน `Engine Noname.ps1`/`Engine Noname.txt`)

## โครงสร้างหลัก: pipeline

การจำลองทั้งหมดคือ pipeline เส้นเดียว (นิยามไว้ในคอมเมนต์บนสุดของ `Parallel Engine Core.ps1`, เดิมนิยามใน `Engine Noname.txt` ก่อนแช่แข็ง):

```
productionPlan -> core -> outputProduction -> customerLayer -> salesLayer -> reorderLayer -> operatingExpenses -> outputSales
```

ตั้งแต่ Patch 6.0.0 แต่ละสเตจคือฟังก์ชันในไฟล์ layer แยกใน `Layers\` (เลข 01-09 นำหน้าชื่อไฟล์ตามลำดับ pipeline) ที่ `Parallel Engine Core.ps1` dot-source เข้ามาทำงานร่วมกันแบบ sequential เหมือนเดิมทุกประการ — ชื่อฟังก์ชันจริงอยู่ในวงเล็บ:

1. **Production Plan** — ข้อมูลดิบ: `$recipe, $costRates, $prices, $stockMax, $reorderThreshold` **อ่านจากไฟล์ JSON ตอนเริ่มรัน** (ตั้งแต่ Patch 5.0.0 ส่วนที่ 2 — ไม่ฝังค่าไว้ในโค้ดเองแล้ว) ดู `Read-DataFile()`/`ConvertTo-Hashtable()` ที่หัว `Parallel Engine Core.ps1` (การโหลด/ตรวจสอบ JSON ยังอยู่ใน orchestrator ไม่ได้แยกไปไฟล์ layer เพราะเป็น bootstrap ครั้งเดียวตอนเริ่มสคริปต์ ไม่ใช่ logic รายวัน — เป็นคนละเรื่องกับชื่อสเตจ "Production Plan" ที่หมายถึงการตัดสินใจยอดผลิตรายวันเท่านั้น) — ถ้าไฟล์ข้อมูลหาย/ขาด key ที่จำเป็น จะ `throw` error ทันที ไม่คำนวณต่อแบบเงียบๆ + `productionOrder` จาก `AutoProductionOrder()` ใน `Layers\01_AutoProductionOrder.ps1` (หรือ player input) — สเตจนี้ชื่อเดิมคือ "Memory Layer" (ตั้งแต่ Patch 1) เปลี่ยนชื่อตอน Patch 6.0.3 เพราะเนื้อหาจริงคือการวางแผนผลิต ไม่ใช่การเก็บความจำแบบที่ชื่อเดิมสื่อ (ดู Patch_Log.txt)
2. **`Normalize-Stock()`** (ใน `Layers\02_NormalizeStock.ps1`) — แปลง stock จากหน่วยที่ใช้แสดงผล (kg/L ตามที่เก็บใน `$stockMax`) เป็นหน่วยที่ใช้คำนวณ (g/mL) เพราะสูตรอาหารกำหนดเป็น g/mL/ฟองไข่ — ตัวคูณแปลงหน่วยอ่านจาก `unitScale` ใน `Stock เริ่มต้น.json` (ไม่ฮาร์ดโค้ดรายชื่อวัตถุดิบในโค้ด) วัตถุดิบที่ไม่ได้ประกาศ `unitScale` จะ `throw` ตั้งแต่ตอนโหลด
3. **`StockCheck()`** (ตัว "core", ใน `Layers\03_StockCheck.ps1`) — คำนวณจาก `productionOrder` ของวันนั้นว่าต้องใช้วัตถุดิบแต่ละอย่างเท่าไร หา bottleneck ratio (`minRatio` เพดานที่ 1 — ผลิตจะไม่ถูก scale ขึ้นเกินยอดสั่ง) แล้วได้ `actualProduced` ต่อเมนู (ปัดลง) **ไข่ถูกแยกคำนวณต่างหาก**จากวัตถุดิบอื่น: รวมยอดใช้ไข่ทุกเมนูแล้วปัด**ขึ้น**เป็นฟองเต็ม ส่วนต่างที่เกินมาคือของเสียซึ่งคิดต้นทุนผ่าน `eggWasteBaht`
4. **`OutputProduction()`** (ใน `Layers\04_OutputProduction.ps1`) — แปลง `actualProduced` เป็น `unitCost`/`totalCost` โดยใช้ `$costRates` และรวมต้นทุนของเสียจากไข่เข้าไปด้วย
5. **`GenerateDailyCustomers()`** (ใน `Layers\05_CustomerLayer.ps1`) — สร้างจำนวนลูกค้าประจำวัน **ตั้งแต่ Patch 5.1.0: อิสระจากประวัติร้านโดยสิ้นเชิง** (ไม่อ้างอิง `history`/ยอดขายเก่าอีกต่อไป) จำลอง "คน `$customerPoolN` คนในละแวก แต่ละคนตัดสินใจแวะเองอิสระต่อกัน ด้วยความน่าจะเป็น `$customerVisitP`" → Binomial(N,p) ใช้ LFSR (Linear Feedback Shift Register) ที่เขียนเอง ไม่ใช้ `Get-Random` — seed จาก system timer ความละเอียดสูงสุด ณ ขณะรัน (ข้อมูลที่คุมไม่ได้) ทอยทีละคนจนครบ N คน นับคนที่ "แวะ" เป็นจำนวนลูกค้าวันนี้ — `N`/`p` คือจุดเกาะสำหรับปัจจัยภายนอกในอนาคต (ดู `Patch Draft.txt`) ฟังก์ชันนี้คือ Customer Layer ตัวจริงหนึ่งเดียว อยู่ใน `Layers\05_CustomerLayer.ps1` — ไม่มีไฟล์ `Customergen..txt` แยกต่างหาก (คนละเรื่องกับการแยก 8 layer ตาม Patch 6.0.0 ซึ่งเป็นไฟล์โค้ดจริงที่ engine dot-source ใช้งานทุกครั้ง ไม่ใช่เอกสารอ้างอิงลอยๆ ที่ไม่มีใครอ่าน)
6. **`SalesLayer()`** (ใน `Layers\06_SalesLayer.ps1`) — จับคู่ลูกค้าที่สุ่มมากับ `availableStock` การเลือกเมนู**ถ่วงน้ำหนักตามราคา** ไม่ใช่สุ่มแบบ uniform: `weight = 1 / price^k` โดย `k = 1.5` คูณด้วย hype item bonus (1.5x) และ diminishing appeal ต่อ คืนค่า `sold`, `remainingStock`, `walkedAway`, `revenue`, `walkAwayChanceHits` (breakdown เสริม แยกเคสเดินหนีเองจากเคสของหมด)
7. **`ReorderLayer()`** (ใน `Layers\07_ReorderLayer.ps1`) — รันหลังจบการขายของแต่ละวัน วัตถุดิบใดที่เหลือต่ำกว่า `$reorderThreshold` ต่อวัตถุดิบ (ไม่ใช่ 10% คงที่ทุกตัว) จะถูกเติมเต็ม ส่วนไข่ เติมโดยปัดขึ้นเป็นหน่วยเต็ม ("เต็มแผง") คืนค่า `reorderCost`, `refilledCost` (breakdown เสริม)
8. **`OperatingExpenses()`** (ใน `Layers\08_OperatingExpenses.ps1`, ตั้งแต่ Patch 6.4.0) — รายจ่ายดำเนินงานที่ไม่ใช่ COGS: ค่าน้ำ+ไฟพื้นฐาน (คงที่/วัน), ค่าไฟเตาอบ (ต่อชิ้นที่ผลิต), ค่าบรรจุภัณฑ์ (ต่อชิ้นที่ขาย) และค่าเช่า (3,500 บาท ทุก 30 วัน — ย้ายมาจาก `OutputSales()` เดิม) รวมเป็น `opExpenseCost` ก้อนเดียวส่งต่อให้สเตจถัดไป
9. **`OutputSales()`** (ใน `Layers\09_OutputSales.ps1`, ตั้งแต่ Patch 6.0.0 — ก่อนหน้านี้เป็น inline calc ท้ายลูปในเอนจิ้นโดยตรง, ตั้งแต่ Patch 6.4.0 ไม่คำนวณรายจ่ายเองแล้ว รับ `opExpenseCost` สำเร็จรูปจาก `OperatingExpenses()`) — สรุปเงินสดปลายวัน: `cashEnd = cashStart + revenueToday - reorderCostToday - opExpenseCostToday`

## ข้อตกลง (convention) ที่ต้องรักษาไว้เวลาแก้ไข

- **หน่วย**: ปริมาณที่ใช้แสดงผล/จัดเก็บ (`stockMax`, `stock`) เป็น kg/L/ฟอง ส่วนการคำนวณสูตรอาหารทั้งหมดทำในหน่วย g/mL/ฟอง การแปลง kg/L→g/mL รวมไว้ที่ `Normalize-Stock()` จุดเดียว — ห้ามเขียนซ้ำที่อื่น และห้ามฮาร์ดโค้ดรายชื่อวัตถุดิบในฟังก์ชันนั้น (อ่านตัวคูณจาก `unitScale` ใน JSON เสมอ)
- **สกุลเงิน**: บาทไทยตลอดทั้งระบบ `costRates` คิดต่อกรัม/มิลลิลิตร/ฟอง ไม่ใช่ต่อ กก./ลิตร
- **การผสมภาษา**: ชื่อตัวแปร/โครงสร้างโค้ดเป็นภาษาอังกฤษ ส่วนคอมเมนต์ คำอธิบายเหตุผล และเอกสารข้อความทั้งหมดเป็นภาษาไทย เวลาเพิ่ม pseudocode ใหม่ให้รักษารูปแบบนี้ไว้ — ไม่ต้องแปลคอมเมนต์ไทยที่มีอยู่แล้ว
- **ไข่มีเคสพิเศษ**: ไม่รวมอยู่ใน bottleneck ratio ทั่วไปของวัตถุดิบอื่น แต่รวมยอดแยกแล้วปัด**ขึ้น** พร้อมคิดต้นทุนของเสียชัดเจน ตรรกะสูตรอาหารใหม่ใดๆ ต้องรักษาความไม่สมมาตรนี้ไว้ ไม่ควรเอาไข่ไปรวมกับ loop `needed`/`ratios` ทั่วไป
- **ระเบียบการทำ patch**: พฤติกรรม engine ใหม่ให้เริ่มที่ `Patch Draft.txt` ก่อน (สถานะ 🔒 หรือ 🟡) ทดสอบ/จำลอง ("Patch Draft Testing Mode" อ้างอิงเป็นช่วงวันจำลอง) แล้วจึง merge เข้า **`Parallel Engine Core.ps1` และ/หรือไฟล์ที่เกี่ยวข้องใน `Layers\`** พร้อมเพิ่ม entry คู่กันใน `Patch_Log.txt` (และลบ/ทำเครื่องหมาย ✅ MERGED ใน draft) — ตั้งแต่ Patch 5.0.0 ไม่ merge เข้า `Engine Noname.txt` อีกแล้ว (แช่แข็ง)
